1. Executive Summary & Problem Statement

In rural and suburban primary healthcare ecosystems, Community Health Workers (CHWs, ASHAs, and ANMs) serve as the primary lifeline for frontline healthcare delivery. However, most health workers rely on manual paper registers, leading to data fragmentation, lost immunization records, unmonitored high-risk pregnancies, and lack of real-time clinical oversight.

The Community Health Worker Assistance Platform is a modern, responsive digital health platform built to digitize community healthcare operations. It empowers health workers to:

  • Register and maintain digital health demographic profiles for community members.
  • Schedule, prioritize, and track home visits, immunization schedules, and clinic appointments.
  • Record clinical vitals (Blood Pressure, Heart Rate, Temperature, SpO2, Blood Glucose, Weight) and diagnose common ailments.
  • Generate structured medication prescriptions and treatment plans.
  • Maintain patient security and account privacy via role-based access control and two-factor OTP verification.

4. Database Schema Specifications

4.1 User Schema (Health Workers & Admins)

  • fullName (String, required, trimmed)
  • email (String, required, unique, lowercase)
  • password (String, minlength: 6, hashed with bcrypt)
  • phone (String, required)
  • role (Enum: "SUPER_ADMIN", "ADMIN", "WORKER", default: "WORKER")
  • isEmailVerified (Boolean, set to true after valid OTP)
  • isApproved (Boolean, auto-approved for frictionless onboarding)

4.2 Patient Schema

  • fullName (String, required), age (Number, 0-120), gender (Enum: "MALE", "FEMALE", "OTHER")
  • phone (String, required), email (String)
  • address, village, district, state, pincode
  • emergencyContactName, emergencyContactPhone
  • bloodGroup (A+, A-, B+, B-, AB+, AB-, O+, O-)
  • allergies, existingConditions
  • registeredBy (ObjectId ref: 'User', audit trail)
  • status (Enum: "ACTIVE", "INACTIVE", default: "ACTIVE")

4.3 Appointment Schema

  • patient (ObjectId ref: 'Patient', required)
  • worker (ObjectId ref: 'User', required)
  • appointmentDate (Date, required), timeSlot (String, e.g. "10:00 AM")
  • purpose (String, e.g. "Antenatal Care", "Child Immunization")
  • priority (Enum: "LOW", "MEDIUM", "HIGH", "URGENT")
  • location (e.g. "Community Health Center", "Village Anganwadi", "Home Visit")
  • status (Enum: "SCHEDULED", "COMPLETED", "CANCELLED", "MISSED")
  • notes, followUpDate

4.4 Health Record Schema

  • patient (ObjectId ref: 'Patient'), recordedBy (ObjectId ref: 'User')
  • recordType (GENERAL_CHECKUP, VITALS, ANTENATAL_CARE, IMMUNIZATION, DIAGNOSIS, PRESCRIPTION, LAB_TEST)
  • vitals: bloodPressure, heartRate (bpm), temperature (°F), spO2 (%), bloodGlucose (mg/dL), weight (kg), height (cm)
  • symptoms, diagnosis, treatmentPlan
  • medications: Array of { name, dosage, frequency, duration }

5. Point-to-Point Operational Workflows

Step 1: Health Worker Registration & Verification

1. User navigates to /register and enters Full Name, Email, Phone, and Password.
2. The frontend triggers POST /api/auth/send-otp.
3. The backend generates a cryptographically secure 6-digit numeric OTP and emails it via Nodemailer.
4. User enters the OTP at /verify-otp.
5. The backend validates OTP expiration (10 min TTL), registers the account with hashed password, and grants active status.

Step 2: Authentication & Session Initialization

1. User enters Email and Password at /login.
2. Backend validates credentials via bcrypt, generates a signed JWT token containing user ID & role.
3. Frontend stores token and user in browser localStorage.
4. Axios HTTP interceptor automatically attaches Authorization: Bearer <token> to all subsequent requests.

Step 3: Dashboard Analytics & Navigation

1. Dashboard fetches live data via concurrent Promise.allSettled calls to /patients, /appointments, and /health-records.
2. Calculates Total Patients, Active Patients, Female vs Male count, Scheduled Visits, and Clinical Records.
3. Interactive stat cards allow direct one-click navigation to respective management modules.

Step 4: Patient Lifecycle Management

1. Registration: Clicking "Register Patient" opens a comprehensive modal with demographic, contact, emergency, and health background fields.
2. Persistence: Dispatches POST /api/patients; record stored directly in MongoDB.
3. Search: Live server-side search querying Full Name, Phone, Village, and District using regex.
4. Editing: In-place modal editing updates patient attributes via PUT /api/patients/:id.
5. Deep Linking: In the patient view modal, health workers can click "Schedule Visit" or "Add Health Record" to immediately start clinical operations for that patient.

Step 5: Appointment Scheduling & Follow-Up

1. Worker opens the Appointments page and clicks "Schedule New Appointment".
2. Selects patient from dropdown, picks visit date, time slot, location, priority (Urgent, High, Medium, Low), and reason tags (e.g. Antenatal Care, Immunization, BP & Sugar).
3. Backend saves the appointment and returns populated patient data.
4. Worker can filter appointments by Status (Scheduled, Completed, Cancelled) or Priority.
5. One-click "✓ Complete" button instantly updates visit status in MongoDB.

Step 6: Clinical Health Records & Vitals Logging

1. Worker logs vitals: Blood Pressure, Pulse, Temperature, Oxygen SpO2, Blood Glucose, and Weight.
2. Categorizes record type (General Checkup, Vitals, Antenatal Care, Immunization, etc.).
3. Enters clinical observations: Symptoms, Diagnosis, and Treatment Plan.
4. Dynamic Prescription builder: Worker clicks "+ Add Medicine" to prescribe multiple drugs with dosage, frequency, and duration.
5. Records are displayed in structured cards with vital indicator pills and expandable clinical detail modals.

Step 7: Account Security & Change Password

1. User clicks the "🔑 Password" button located in the global header.
2. Enters Current Password, New Password, and Confirm Password with eye visibility toggles.
3. Frontend validates minimum 6 characters and password matching.
4. Backend verifies current password hash via user.comparePassword() and updates it with an auto-generated fresh bcrypt hash.
